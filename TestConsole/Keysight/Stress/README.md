# Нагрузочный режим Keysight в TestConsole

Режим существующего TestConsole для длительного опроса Keysight 34465A по
Ethernet (SCPI, порт 5025). Основное приложение АСК запускать не требуется.
Режим не инициализирует БД и использует прямой TCP-клиент. Зависимости и
требования к установленным runtime остаются штатными для TestConsole.

## Запуск

Подключите прибор и компьютер к одной сети, узнайте IP прибора. Запустите
`TestConsole.exe`, выберите пункт **23** и введите IP. После Ctrl+C происходит
возврат в главное меню. Для запуска напрямую передайте команду `keysight-stress`:

```powershell
.\TestConsole.exe keysight-stress 192.168.1.16
```

Прибор можно оставить без измерительных проводов. Утилита устанавливает режим
измерения ёмкости. На разомкнутом входе значения и перегрузка не оцениваются как
брак: цель — проверить обмен. Воспроизведение исходного сбоя не гарантировано.

По умолчанию работает до Ctrl+C, без задержек между успешными измерениями,
с тайм-аутом одной операции 10 секунд.
На экране отображаются команды, ответы, длительность, счётчики. JSONL-журнал
пишется с немедленным сбросом каждой записи в `logs` рядом с приложением.
Для длительного прогона следите за размером журнала и свободным местом.

```powershell
# 100 измерений, ожидание до 3 секунд вместо стандартных 10 секунд
.\TestConsole.exe keysight-stress 192.168.1.16 --cycles 100 --timeout 3000
# Другой порт, пауза и путь журнала
.\TestConsole.exe keysight-stress 192.168.1.16 --port 5025 --delay 100 --log .\logs\experiment.jsonl
```

`--timeout` — предел всей одной операции (подключение + запись + чтение), мс.
`--cycles 0` — непрерывный запуск. `--delay` — пауза между циклами, мс.
`--help` — справка. Существующий файл журнала не перезаписывается.

## Последовательность

1. Подключение → `*IDN?` (проверка модели 34465A) → `CONF:CAP` → `FUNC?`.
   После успешной инициализации — пауза 5 секунд для подключения конденсатора.
   Ctrl+C отменяет ожидание. Пауза повторяется при новой полной инициализации после сбоя.
2. `MEAS:CAP?` → следующий запрос сразу после полного ответа.
3. При ошибке: закрытие TCP, повтор измерения на новом соединении.
4. После двух неудачных измерений: один `*IDN?`; при подтверждении модели ещё
   два запроса измерения. Ошибка идентификации завершает текущий цикл.
5. После окончательной ошибки цикла: пауза 1 с, затем новая инициализация и цикл.
6. Ctrl+C отменяет текущий запрос/паузу и записывает итоговые счётчики.

Все запросы последовательны; командная очередь намеренно не переполняется
параллельными запросами. `*RST`, `*CLS` и чтение `SYST:ERR?` не выполняются:
очередь ошибок прибора остаётся доступной для последующего исследования.

Восстановление измерения повторяет порядок `MultimeterMeasurementQuery` из АСК.
Это самостоятельный диагностический клиент, а не точная копия транспорта АСК:
он читает ответ до LF (включая фрагментацию TCP), ограничивает всю операцию
тайм-аутом, не запускает усреднение, коммутацию, UI и внешнюю watchdog-оболочку.
В журнале `transportErrors` учитывает и ошибки, после которых восстановление
успешно; `failed` — только окончательно неудачные циклы.

Коды завершения при прямом запуске `keysight-stress`: `0` — ошибок обмена не было; `1` — были ошибки, включая
восстановленные; `2` — ошибка аргументов/журнала. Ctrl+C сам по себе не ошибка.

## Сборка и проверка

```powershell
dotnet build TestConsole/TestConsole.csproj -c Release
python TestConsole/Keysight/Stress/verify.py
# Прямой запуск без меню
dotnet run --project TestConsole/TestConsole.csproj -c Release -- keysight-stress 192.168.1.16
```

`verify.py` проверяет клиент через локальный TCP-имитатор: фрагменты ответа,
перегрузку, тайм-аут, закрытие соединения, восстановление, неверную модель,
некорректный результат и постоянное отсутствие ответа. Реальный прибор не нужен.
